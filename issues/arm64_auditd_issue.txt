ARM64 AuditD / Splunk Universal Forwarder Investigation
Status: Unresolved (environment abandoned)
Decision: Rebuild lab on Windows x86_64

Goal:
Build a Splunk + MCP + Universal Forwarder + AuditD lab for AI-assisted Linux attack demonstrations.

Environment:

MacBook host
ARM64 Ubuntu VM (Vagrant)
Splunk Enterprise
Splunk Universal Forwarder
AuditD
MCP server

Initial state:
Environment worked initially.
AuditD events were successfully generated and ingested into Splunk.
Sensitive file monitoring worked during earlier tests.

Problem observed:
AuditD events stopped arriving in Splunk in real time.

Symptoms:

Universal Forwarder remained healthy.
Internal Splunk logs continued ingesting.
Audit log file showed valid new events.
Splunk displayed unexpected null-byte events (\x00\x00\x00...).
Rebooting the VM caused a batch of old AuditD events to appear.
New events after reboot again stopped streaming.

Initial hypotheses:

Broken inputs.conf
Fishbucket corruption
AuditD log rotation
CRC/checkpoint issue
Binary file detection
Splunk parsing issue
ARM64 compatibility issue

Actions taken:

Inputs validation
Verified monitor stanza.
Added:
crcSalt=<SOURCE>
initCrcLength
Removed experimental settings.

Result:
No improvement.

Fishbucket reset
Deleted:
/opt/splunkforwarder/var/lib/splunk/fishbucket/*
Restarted UF.

Result:
No improvement.

Internal log analysis
Observed:
Null-byte events also appeared in splunkd internal logs.

Interpretation:
Not limited to AuditD file.

Alternative file ingestion tests
Created:
/tmp/test.log
/tmp/live.log

Result:
Realtime ingestion worked normally.

Conclusion:
UF tailing functionality itself appears healthy.

AuditD validation
Verified:
audit.log contains valid text.
no null bytes in file.
events visible via tail -f.
audit rules firing correctly.

Conclusion:
AuditD writing itself appears functional.

Reboot experiments
Observation:
After full VM reboot:
historical AuditD events arrive in batch
realtime streaming stops again

Conclusion:
Issue survives UF restart.
Full OS reboot temporarily resets behavior.

Timestamp investigation
Extracted:
msg=audit(epoch:id)

Observation:
Different classes of AuditD events produced inconsistent epoch values.

Examples:

USER_* / service events appeared offset in one direction
PATH / SYSCALL / rule-generated events appeared offset differently

Observed behavior:

identical actions grouped correctly
timestamps inconsistent across event categories
Splunk timeline became misleading

Additional observations:

VM system time itself appeared correct:
date
date -u
timezone
Issue appears lower-level than Splunk parsing.

Final working hypothesis:
Environment-level instability involving:

ARM64 VM
AuditD timestamp generation
file notification / tailing interaction
checkpoint behavior

Universal Forwarder itself does not appear to be root cause.

Decision:
Stop investing time.

Next iteration:
Rebuild entire demo environment on Windows desktop.

Target stack:

Windows host
VirtualBox
Ubuntu x86_64
Splunk Enterprise
UF
AuditD
MCP

Approach:
Build incrementally.
Snapshot after each working stage.
Record only after successful rehearsal.

Lessons learned:

Validate telemetry before detections.
Separate ingestion from parsing.
Preserve failed labs.
Experimental environments can create misleading debugging signals.
